# 9router host enrollment

Do not run this installer until central CI passes on ARM64 and AMD64, the full platform commit is reviewed, and the app repository caller is disabled with all legacy workers finished. This deployment does not change ACB, Messenger, shared Traefik middleware, Docker daemon, or Cloudflare.

1. Verify the central commit SHA against the reviewed checkout; verify `git status --short --branch`, worktrees, and the immutable app commit. Review the public SSH key, known host key, current route bytes, mounted dynamic directory, active container config IDs/digests, and private runtime environment. Back up legacy script/Compose/state and the active route outside the watched directory. Hold the original `/opt/9router/.deployment.lock` from adoption through cutover. Do not print secrets.
2. With root credentials, run `bash install/install.sh --check --release <40-hex-central-commit> --app-source <absolute-app-checkout> --app-ref <40-hex-app-commit> --public-key <reviewed-ed25519-public-key-file>`. The checkout must match the commit exactly. The installer never generates a private key. Then run the identical command without `--check`; examine root-owned registry and SSH forced key. Its output does **not** mean the app was adopted, the timer enabled, or production cut over.
3. Operator: compare `docker compose --env-file /etc/vps-deploy/apps/9router/runtime.env -p 9router -f /opt/vps-deploy/current/apps/9router/docker-compose.prod.yml config` with each live container environment, mounts, networks, and optional bridge socket without logging values; correct profile/env under root review before adoption. Verify the RTK network is internal. Run `/opt/vps-deploy/current/bin/deployctl adopt --app 9router`; then `status --app 9router --strict`. Adoption must not alter route/container.
4. Confirm the restricted key cannot run `id`, SCP/SFTP, port forwarding, or alternate sudo; permit only forced-command JSON stdin. Use pinned `StrictHostKeyChecking=yes`, `BatchMode=yes`, `IdentitiesOnly=yes`. Send same deployed app digest under a fresh request ID; poll `status`, verify route ACK, identity and drain. Roll back via a fresh `rollback` request (only retained previous image/container), then same-digest redeploy. Send an RTK same-digest request and confirm no recreate.
5. If a request is interrupted or reports `recovery_required`, do **not** restart the legacy writer or stop either slot; issue explicit `reconcile` with the matching component after inspecting durable intent/snapshot/route and public identity. Divergent routes require manual investigation. `cleanup-drains` only stops known-idle inactive containers. Enable the drain timer only after canary verification. Finish caller switch, remove old repo-specific secrets before re-enabling workflows, keep the original lock until legacy executables and writers retire.

The global route lock coordinates only participating publishers, not ACB/Messenger. Two slots share SQLite: rollback changes image and route, **not** database migrations. No scheduled reconcile/failover. Credentials, app env, private profile, snapshots, and request contents must not enter the public repository.
